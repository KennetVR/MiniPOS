# Native MiniPOS Mobile Client and Shared Supabase Inventory
Objective: Deliver an installable native mobile MiniPOS client and make desktop and mobile share one cloud inventory.
Branch: `feat/native-mobile-supabase`; delivery strategy: `ask-on-risk` (default); forecast: approximately 2,500 authored lines; checks: desktop `npm run typecheck`, mobile tests/build, and available Supabase contract checks.

## Specs

### S1 — Native mobile application
User requirement: “No no quiero que sea web. quiero que sea netamente la misma applicacion pero una adaptada a movil”
Scope: Add an installable native mobile client for the existing MiniPOS product; do not deliver a web/PWA substitute. Use React Native with Expo as an implementation assumption because the existing project is TypeScript/React; target Android and iOS unless platform evidence prevents it.
Acceptance: Mobile has native navigation and touch-sized screens for the existing MiniPOS workflows (dashboard, products, POS, categories, users, and settings), connects to the same account and authoritative data as desktop, and provides the barcode inventory intake workflow in S4. Do not claim full parity until each existing user-facing workflow is represented and checked.
Checks: Typecheck and focused mobile tests; run a mobile build/export if the local toolchain supports it. Android SDK/ADB was not found during initial environment inspection, so device/emulator verification is currently pending.

### S2 — One cloud inventory shared by desktop and mobile
User requirement: “Listo, entonces si quiero que compartartir el mismo inventario y sincronizar tbm” and “La segunda opción” (access from anywhere on the internet).
Scope: Supabase is the selected cloud provider. PostgreSQL is authoritative for desktop and mobile business data; keep the existing lowercase table names for `categoria`, `proveedor`, `producto`, `venta`, `detalle_venta`, `entrada_inventario`, `detalle_entrada`, `movimiento_stock`, `ingreso`, `egreso`, and `configuracion`. Preserve the desktop-used product description, purchase/sale prices, minimum/current stock, supplier/category, active status, and timestamps; sale invoice number/subtotal/discount/tax/total/status/void reason; receipt total/status/date and line subtotals; stock movement before/after/delta/reference; income/expense fields; and settings key/value/description. Use Supabase Auth UUIDs mapped through a `profiles` row with the existing administrator/seller roles. Business record IDs remain numeric; profile identity is the authenticated UUID. Provide transactional RPCs: `create_inventory_receipt(p_id_proveedor bigint, p_numero_comprobante text, p_items jsonb)` where each item has `id_producto`, `cantidad`, and `precio_compra`; `create_sale(p_detalles jsonb, p_forma_pago text, p_descuento numeric)` where each item has `id_producto`, `cantidad`, and optional per-unit `descuento`, and the server derives authoritative prices; `adjust_inventory(p_id_producto bigint, p_stock_real integer, p_motivo text)`; `create_expense(p_fecha date, p_tipo text, p_concepto text, p_monto numeric, p_comprobante text, p_beneficiario text, p_id_proveedor bigint)`; `create_product(...)`; and `void_sale(p_id_venta bigint, p_motivo text)`. These operations derive the actor from `auth.uid()`. Receipt/sale/adjustment/product/void RPCs atomically update stock and record details/movements; sale also records income; expense creation is administrator-only. RPCs return the numeric created record ID where applicable; callers fetch the record for display fields. Direct product metadata writes may not update stock; all stock changes must use the RPCs. No deployment, account provisioning, credential entry, or transfer of local database contents is authorized by provider selection alone.
Acceptance: Both clients observe changes to shared products and stock through the same Supabase project; concurrent stock updates cannot silently overwrite each other; offline/unavailable connectivity is reported rather than presented as a successful sync.
Checks: Contract tests for shared data operations and atomic stock updates; static checks for RLS and absence of service-role secrets in clients; no remote deployment or data upload during implementation.

### S3 — Secure shared authentication and authorization
Scope: Use Supabase Auth email/password and server-enforced authorization for both clients. Keep privileged service-role credentials out of desktop/mobile bundles. Preserve role distinctions for administrator and seller operations where supported by existing application behavior; policies/RPCs must derive the actor from `auth.uid()` and the mapped profile, not trust a client-supplied user ID. Disable public signup; invited Auth accounts receive a seller profile, and administrators manage role/active status. Existing SQLite users and passwords remain untouched until an explicitly authorized migration plan exists; cloud accounts require trusted invitation/provisioning.
Acceptance: Unauthenticated or unauthorized users cannot read or mutate protected inventory; privileged actions are enforced by database policies/RPCs, not only by hidden UI controls.
Checks: Auth/RLS policy tests or a documented unavailable local Supabase test environment; inspect built client configuration for secret leakage.

### S4 — Barcode inventory intake
User requirement: “Claro escanear un producto y su cantidad”
Prior agreed workflow: scan a product once, then enter the received quantity; an unknown barcode may open product creation with that barcode prefilled.
Acceptance: Native mobile scanning identifies an existing product or offers creation for an unknown barcode; quantity is entered explicitly; confirming records an inventory receipt and updates the shared stock atomically; duplicate submission and invalid quantities are rejected visibly.
Checks: Focused tests cover known/unknown barcode, quantity validation, successful receipt, rejected receipt, and repeated/concurrent requests.

### S5 — Preserve local data and avoid unapproved remote side effects
Assumption: Existing local SQLite data may be valuable. Keep it unchanged and do not upload it, create/link a Supabase project, or deploy cloud resources without explicit authorization for the exact project, operation, and credentials/session.
Acceptance: Implementation provides configuration/setup guidance without embedding credentials; local SQLite remains intact; any future import is explicit, reviewable, and non-destructive.
Checks: Verify no local DB/data file is staged or modified; verify secrets are supplied by environment/configuration and ignored by Git.

### S6 — Verification and handoff
Scope: Add automated checks for new behavior and update setup/architecture guidance to distinguish implementation from required user-provided Supabase configuration and deployment.
Acceptance: Required commands and environmental limitations are recorded honestly; no test is claimed to pass without an observed run.
Checks: Desktop typecheck, mobile tests/build where available, and parent spot-check of each delegated result.
